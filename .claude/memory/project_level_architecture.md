The level system is being built in deliberate layers, each enabling the next:

1. **Modular builders (done 2026-05-02).** `level_builder.gd` was a 1080-line god object; now it's a ~160-line orchestrator that dispatches to focused subsystems under `game/scripts/level/build/` (FloorBuilder, WallBuilder, PitBuilder, CeilingBuilder, LightingBuilder, DoorBuilder, DecalBuilder, EnemySpawner, GroundBuilder, InteractableBuilder, PuzzleBuilder). All state lives in `LevelBuildContext` (RefCounted); builders are stateless static methods.

2. **Declarative graph layout (done 2026-05-02).** `game/scripts/level/graph/` defines `LevelGraph` (anchor + rooms + connections + puzzles), `RoomNode`, and `Connection`. `GraphSolver.solve(graph)` resolves into `Array[LevelPiece]`. `LevelLayout` accepts either `pieces` (legacy) or `graph` (declarative); graph wins when both are set. **Constraint:** connections must use opposite walls only — T-junctions are expressed via small junction rooms, not bent corridors. Single-corridor bends are a future feature on the same model.

3. **Interactable slots + puzzle layer (done 2026-05-02).** `RoomDef.slots[]` declares spawn points (id + scene + offset + rotation_y). `InteractableBuilder` materialises them and registers in `BuildContext.slots` keyed `"{room_id}.{slot_id}"`. `LevelGraph.puzzles[]` is an `Array[PuzzleDef]` where `PuzzleDef` is a polymorphic Resource base — built-in templates (`SwitchDoorPuzzle`, `BossKillDoorPuzzle`) plus designer-authored subclasses. `PuzzleBuilder.apply_all` runs after geometry, builds a `Connection.id → door` map, dispatches each puzzle's `apply(ctx, slots, doors)`. `PrototypeDoor.setup_lock(unlocks, locked, on_boss)` is the public API puzzles use to set lock state post-_ready. Test fixture: `resources/level/layouts/test_level.tres` + `scenes/world/level_shell.tscn`.

4. **Procgen scaffolding (done 2026-05-02).** `game/scripts/level/procgen/` defines `LevelGenerator` (polymorphic Resource base, `generate() → LevelGraph`, with shared `pick_by_role` helper), `RoomTemplate` (room + role + weight), `LinearGenerator` (east chain only), and `BranchingGenerator` (east chain with junction templates and 1-room dead-end branches; can emit a SwitchDoorPuzzle locking the final connection with switches placed in branches). `LevelLayout.generator` wins over `graph` and `pieces`. Generators emit RoomNode ids like `r0..rN` (chain) and `b1..bN` (branches), wrapping shared RoomDef templates — `LevelPiece.room_id` and `LevelPiece.additional_slots` were added so the builder uses per-instance identity (not the template's `RoomDef.id`) when registering doors and slots, which is what makes template reuse safe.

5. **Player spawn + connection-driven doors + per-instance slots (done 2026-05-02).** `prototype_player_spawn.tscn` is a Marker3D with a script that joins the `&"player_spawn"` group; `prototype_root._move_player_to_spawn()` finds it after build and calls `player.set_spawn_position()` (sets both the current position and the post-death respawn anchor). `Connection.has_door: bool` lets generators add doors without mutating shared RoomDef templates; `BuildContext` indexes these into `connection_doors` and `LevelBuilder` consults both `RoomDef.door_openings` and `connection_doors`. `RoomNode.additional_slots` flow through `GraphSolver → LevelPiece → InteractableBuilder`, layered on top of `RoomDef.slots`.

6. **Boss + exit slot integration (done 2026-05-02).** `prototype_boss_spawn.tscn` is a marker that, on `_ready` and on `reset_state` (NG+), acquires from `EntityPool`, sets `is_boss=true`, and spawns the boss at its position — full layout-driven replacement for `prototype_root._spawn_boss`. `prototype_exit.tscn` works as a slot scene with no changes (already auto-joins `&"boss_listeners"` and dispatches `&"level_reset_handler"` on interact). `proto_end_room.tres` is now a 12x12 boss arena with boss + exit slots — completes the gameplay loop (chain → switches → unlock → boss → exit → NG+) on a fully generated level. Legacy prototype scenes still use `spawn_boss_on_ready` + scene-positioned boss/exit; new levels use slots.

7. **Multi-room branches + difficulty + loot (done 2026-05-02).** Branches in BranchingGenerator are now 1-N rooms deep (`min_branch_depth`/`max_branch_depth`). New `branch_linear_ns` template role for through-traffic interior branch rooms; existing `branch_north`/`branch_south` are now terminator-only. Switches go on terminators (one per branch, regardless of depth) so deeper branches mean more rooms to clear before the same one switch. `LevelPiece.enemy_level_range: Vector2i` (mirrored on `RoomNode`) propagates per-piece difficulty; BranchingGenerator scales by chain index (interior `(i, i+1)`, branches `(base+0, base+2)` where base = junction_index+1, boss arena `(length, length+1)`). Loot crates are placed on each branch terminator (`place_loot_at_branches` flag) — exploration reward.

8. **ClearRoomPuzzle template + procedural emission (done 2026-05-02).** New PuzzleDef subclass: locks a door behind clearing all enemies inside a target room (snapshots enemies in the room AABB at apply time, one-shot-connects each `died` signal to door.unlock(), uses unlocks_required = enemy count). `BuildContext.pieces_by_id` (room_id → LevelPiece, rooms only) populated by LevelBuilder so puzzles can do AABB queries. `BranchingGenerator.lock_branch_with_clear_chance` (default 0.5) optionally locks each branch entrance behind a ClearRoomPuzzle on the junction — player must clear chain enemies in the junction before exploring the branch.

9. **Per-piece theming (done 2026-05-02).** `RoomDef.theme_override` and `CorridorDef.theme_override` (both nullable) let any piece swap its visual theme. `BuildContext.apply_theme(theme)` rebuilds the active material set with caching (`_material_cache: theme → {wall, floor, wall_alt, floor_alt}`) so repeated overrides are cheap. `LevelBuilder` applies the override before each piece build and restores `layout.theme` after. **Geometry constraint:** override themes should share `wall_height` / `wall_thickness` / `opening_width` with the layout theme — the wall mesh cache is keyed on size only, so mismatched geometry would carry over between pieces. Demo: `resources/level/themes/amber_theme.tres` (warm/orange palette) applied to the vault room in `test_level_graph.tres`. For procgen-driven theming, `RoomNode.theme_override` + `LevelPiece.theme_override` pass-through is the natural follow-up — not yet built.

10. **GridGenerator + corridor pool + content variety (done 2026-05-02).** `BranchingGenerator.corridor` → `corridor_pool: Array[CorridorDef]` with random per-connection picks (`branch_corridor_pool` falls back when empty). New corridor variants in `resources/level/corridors/` (standard, long, dim). New room templates: `proto_pit_linear` (W+E with central pillar over a pit — jump puzzle as a chain step), `proto_wide_linear` (10x8 with 2 enemies). `LevelGenerator.pick_by_openings` static helper picks templates by structural opening-set match (alongside the existing `pick_by_role`). New `GridGenerator` (polymorphic LevelGenerator subclass) — fills a `grid_width × grid_height` grid with rooms, picks templates by opening-set match, emits connections to all adjacent occupied cells (creates cycles). **Cycle constraint:** GridGenerator picks ONE corridor per axis (east-going + south-going) so multiple paths to the same cell compute consistent positions; per-edge random picks would trigger GraphSolver position-mismatch warnings. 9 grid-cell templates authored covering every opening combination needed for a dense grid (4 corners, 4 T-junctions, 1 cross). `procgen_grid_demo.tres` is the test fixture; v1 skips boss/exit/puzzles for pure navigation demo.

11. **GridGenerator playability (done 2026-05-02).** GridGenerator gains `boss_cell` / `exit_cell` (Vector2i, default `(-1,-1)` = unset) and `boss_level_range`. When set, those cells receive the boss spawn / exit slots via `additional_slots`, with offsets so they don't overlap when the same cell hosts both. Optional `emit_switch_puzzle` locks **every** connection touching the boss cell behind its own SwitchDoorPuzzle (locking only one would leave bypass routes through the corner's other entry). Each door gets `switch_count` switches drawn from a shared pool of non-special cells; cells consumed by one puzzle aren't reused by the next. Deterministic Fisher-Yates shuffle uses the seeded rng so puzzle placement is reproducible. `procgen_grid_demo.tres` now sets boss/exit at SE corner (2,2) with switch_count=2 — fully playable navigation+combat+puzzle loop in the grid topology.

12. **Future procgen work.** Open: sparse grids (terminator + 2-opening straights for partial occupancy + reachability solver), generator composition (meta-generator stitches multiple regions/themes together), bent corridors, more puzzle types (sequenced switches, key/door, pressure plates), template authoring variety. Architecture is complete enough that the prototype scene can be retired in favour of `level_shell.tscn` + a graph or generator layout.

**Why:** Solo dev plans tens to hundreds of levels of varying scale. Hand-placing every piece by Vector3 doesn't scale; a god-object builder makes every new piece type a cross-cutting change.

**How to apply:** New levels should be authored as `LevelGraph` `.tres` files, not `LevelPiece` arrays, and use slots + puzzles instead of scene-placed interactables + scene-level wiring. The prototype_3d.tscn / prototype_layout.tres are the legacy holdouts — slated for retirement once the new test bed (level_shell.tscn / test_level.tres) covers their feature set. Don't add a new piece type without splitting it across the existing builders. When picking up procgen, emit complete graphs (rooms + connections + puzzles); do not bypass the solver, slots, or puzzle dispatch.
